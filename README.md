# Absorbobot

В этой ревизии реализованы конфигурация, проверки, установка собственных
units, API `Store`, локализованный диалог и административные действия.
Обработка входов и изолированное выполнение ещё интегрируются: `serve`
пока не является завершением установки работающего сервиса. Контракты
диалога проверены через настоящий aiogram transport на изолированном
локальном HTTP-сервере, не в настоящем Telegram.

Telegram-интерфейс к [Absorbent](https://github.com/ivan-mikhnovich/absorbent):
конспекты лекций из аудио, видео и YouTube с дополнительными материалами.
GNU GPL v3 или более поздняя версия. Логотип в `src/absorbobot/assets/absorbent.jpg`
взят из Absorbent и распространяется на тех же условиях.

## Раздельная установка

Python не ниже 3.13 и `uv`. Окружение бота не содержит torch или Absorbent:
ядро устанавливается отдельно как non-editable `uv tool` из фиксированного
релиза. Рабочая копия разработки ядра не используется. Для этого развёртывания
выбран Absorbent **0.1.2** из `ivan-mikhnovich/absorbent`; бот устанавливается
из полного опубликованного SHA репозитория `ivan-mikhnovich/absorbobot`.
Проверка требует non-editable receipt установленного инструмента, полный
commit и `dirty=false`, но не закрепляет в коде единственную версию ядра.
Установка из `uvx` без receipt отклоняется.

```bash
export UV_TOOL_BIN_DIR="$HOME/.local/share/absorbobot/bin"
uv tool install --force 'git+https://github.com/ivan-mikhnovich/absorbent.git@v0.1.2'
uv tool install --force "git+https://github.com/ivan-mikhnovich/absorbobot.git@${ABSORBOBOT_COMMIT:?Укажите полный опубликованный SHA}"
```

`ABSORBOBOT_COMMIT` — идентификатор проверенного опубликованного коммита,
сохранённый оператором при развёртывании, не имя ветки. Установленный бот
сам не обновляет ни себя, ни ядро.

Единственный каталог моделей — серверная конфигурация Absorbent.
Проверка установленного ядра возвращает модели, defaults, расширения входов
и runtime-пути без значений API-ключей. Дополнительная модель без ключа
остаётся в каталоге, но её выбор нельзя принять в обработку; ключи
проверяются для выбранных провайдеров, не для всех необязательных моделей.

## Конфигурация

Скопируйте [`examples/config.yaml`](examples/config.yaml) в
`~/.config/absorbobot/config.yaml` и настройте пути и `admin_ids`.
`absorbent_config` указывает на отдельный серверный YAML ядра, не на файл
в рабочей копии разработки. Пустой список администраторов отклоняется.

Секреты хранятся только в `~/.config/absorbobot/secrets.env`, принадлежащем
владельцу сервиса, с правами `600`. Имена переменных:

- `ABSORBOBOT_TOKEN` — токен этого бота.
- `TELEGRAM_API_ID`, `TELEGRAM_API_HASH` — application credentials для
  официального локального Telegram Bot API, не токены другого бота.
- API key env names, указанные в серверном YAML Absorbent, например
  `DEEPSEEK_API_KEY`.

При ручном запуске CLI файл разбирается без shell и интерполяции;
уже заданные переменные окружения процесса имеют приоритет. В user systemd
значения сначала загружаются из `EnvironmentFile`, поэтому для смены
секретов изменяют защищённый файл и перезапускают соответствующие службы,
а не рассчитывают на окружение интерактивной оболочки. Native API дополнительно
удаляет bot/cloud ключи через `UnsetEnvironment`. Секреты не попадают в YAML, SQLite-снимки моделей,
argv или опубликованный репозиторий. Проверки не печатают секреты.

До установки units должны быть готовы оба Python-инструмента, native
`telegram-bot-api`, серверные YAML и секреты. После первого переключения
бота с облачного API через `logOut` порядок подготовки такой:

Помимо Python-зависимостей обязательны `bwrap`, `ffmpeg`, `ffprobe`,
`pdfinfo`, `pdftoppm`, `soffice`, `pandoc`, `lualatex`, `kpsewhich` и `bun`.
LuaLaTeX должен иметь собранный format и установленные TeX-корни: их
обнаружение проверяет metadata probe ядра. `uv` и native `telegram-bot-api`
также должны быть доступны по настроенным путям; pip-зависимости бота эти
системные программы не устанавливают.

```bash
uv tool run --offline --no-config absorbobot check-storage --config ~/.config/absorbobot/config.yaml
uv tool run --offline --no-config absorbobot install-units --config ~/.config/absorbobot/config.yaml
systemctl --user start absorbobot-api.service
uv tool run --offline --no-config absorbobot check --config ~/.config/absorbobot/config.yaml
systemctl --user start absorbobot.service
```

`check` требует уже работающего локального API. Его успех подтверждает
preflight и идентичность бота, но не заменяет проверку реального диалога,
обработки лекции и доставки файлов.

`check-storage` проверяет только backing mount, доступность записи и
свободное место: не читает секреты, не обращается к API и не создаёт
каталоги. `check` — read-only preflight: проверяет зависимости, установленное
ядро и `getMe` локального Bot API с username `absorbobot`; не обрабатывает
лекции и не отправляет сообщения. `install-units` записывает только
`absorbobot.service` и `absorbobot-api.service` в пользовательский systemd
и выполняет `daemon-reload`, но не запускает сервисы и не меняет чужие units.
После проверки mount команда создаёт собственные рабочие каталоги служб;
символические ссылки вместо этих каталогов или собственных units отклоняются.
Пути в units берутся из выбранной конфигурации; устаревшие собственные units
после изменения путей выявляются проверкой.

Локальный сервер Bot API обязателен для больших записей. Он слушает только
loopback на порту 8081. Обычный облачный Bot API не используется как
неявный запасной вариант. Перед переключением требуются собственные
application credentials и корректная установка native `telegram-bot-api`.

## Хранение и транзакции

`storage_dir` должен находиться на явно указанном `backing_mount`
(по умолчанию `/media/storage`), не на корневом диске. Mount и свободное
место проверяются до создания UUID-каталогов; запасного каталога на SSD
нет. Большие файлы располагаются в `storage_dir/jobs/<UUID>/input`,
`output` и `tmp`. Данные сохраняются до явного удаления администратором.

Для SQLite оператор выбирает SSD: `state_dir/absorbobot.sqlite3` должен
находиться вне backing mount; используются WAL, foreign keys и транзакции
`BEGIN IMMEDIATE`. Проверки отвергают размещение на backing mount и NTFS/fuseblk,
но не определяют физический тип накопителя.
Draft сохраняет UUID даже при отказе или закрытии; принятому заданию
присваивается тот же UUID. Новый draft не меняет snapshot принятого задания.

Квота учитывает принятые запуски за скользящее окно, включая queued,
failed и cancelled. Ровно на границе окна слот освобождается. Повторное
нажатие не создаёт второе задание. Администратор обходит только квоту,
не FIFO, пределы входа или последовательность обработки.

Полный результат — исходное задание `completed`, разрешённый владелец,
`files_deleted=false` и существующие `notes.md`, `notes.html`, `notes.pdf`,
`notes.zip`. Для reuse должен совпадать `input_signature`: `Store` сравнивает
переданную подпись, а эквивалентность входов определяет модуль приёма.
Повторная выдача полного результата не создаёт job и не расходует квоту;
расход CPU/API исходного задания не переносится получателю. Поздний reuse
освобождает зарезервированный слот только после выбора готового результата.
Выбор нового запуска проверяет квоту повторно и возвращает задание в конец
очереди с новым accepted time.

Отмена активного процесса сначала сохраняет намерение; process binding
удаляется только после остановки и reap. После прерывания jobs в состояниях
`preparing`, `running`, `cancel_requested` и drafts в `preparing` получают
`status=failed`, `failure_reason=interrupted`. Drafts `collecting`/`ready`,
queued jobs и ожидание reuse сохраняются.
`purge` удаляет только собственное UUID-дерево terminal job либо допустимого
неактивного draft; история, usage и квота остаются. Удаление reused job
не удаляет чужой исходный результат. Native API database/cache не является
UUID-деревом и этим действием не очищается.

Telegram update ID, изменения состояния и outbox фиксируются атомарно.
Исходящие действия выполняются отдельно; сетевой сбой доставки не должен
повторно запускать обработку лекции. Bot API не предоставляет client
idempotency: при неизвестном исходе отправки сообщение может повториться.

## Диалог и доступ

Бот принимает только личные обращения допущенных пользователей.
Администраторы из `admin_ids` допущены всегда; остальным нужен
`/allow <numeric_user_id> [подпись]`. Проверяется отправитель сообщения
или callback, не username, chat ID или автор пересланной записи.
Неодобренные пользователи и группы не получают ответа; их файлы не загружаются.

Команды: `/start`, `/new`, `/jobs`, `/settings`, `/language`, `/help`,
`/cancel`, `/stats`, `/version`. Приветствие содержит логотип, возможности,
ограничения, предупреждение о хранении и облачных моделях, лицензию,
репозитории и фактическую версию ядра с полным commit.
Начальный язык берётся из Telegram (`ru` либо `en`) и сохраняется.
Язык конспекта следует интерфейсу до явного переопределения; сброс возвращает
актуальные серверные defaults и режим «Как интерфейс».

Составление лекции: одна запись либо YouTube, затем упорядоченные материалы,
«Файлы добавлены», настройки и подтверждение сводки. Вторая запись не склеивается
с первой: замена требует подтверждения и нового UUID. Незавершённый импорт
не позволяет подтвердить сводку. В разделе дополнительных параметров доступны
все модели текущего каталога и числовые параметры ядра; нечисловые,
бесконечные и недопустимые значения отклоняются без скрытого ограничения.
Исчезнувшую модель требуется выбрать заново, а не молча заменить.

`/jobs` показывает собственную историю. Обычному пользователю `/stats`
показывает только его время, доступные ресурсы и квоту, без денежных показателей.
Администратору `/stats` без аргумента показывает общую статистику с оценкой
расходов; `/stats <numeric_user_id>` — показатели выбранного пользователя.
Для своей истории администратор указывает собственный числовой ID.
Отмена требует подтверждения; активная работа считается остановленной только после reap.
Кнопки используют одноразовые сохранённые tokens, привязанные к отправителю
и действию; повторный update или подтверждение не создаёт второй запуск.

Администратору доступны `/admin`, `/queue`, `/allow`, `/ban`, `/users`,
`/job <UUID>`, `/stats [numeric_user_id]`, `/storage`, `/purge <UUID>`,
`/pause`, `/resume`. Ban, точечная отмена и purge требуют подтверждения.
Настроенного администратора нельзя заблокировать. Пауза сохраняется
и не прерывает текущую работу. Административная история запрещённых пользователей
остаётся доступной; оценка расходов отделяет известную сумму от неполных вызовов.

## Разработка

```bash
uv run pytest
```

Тесты SQLite изолированы; они не используют настоящие секреты или
Telegram-аккаунты. Публикация включает только код, лицензию, логотип и
configuration example, не env, базы, сессии, логи или записи лекций.
