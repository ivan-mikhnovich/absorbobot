# Absorbobot

Telegram-интерфейс к [Absorbent](https://github.com/ivan-mikhnovich/absorbent):
конспекты лекций из аудио, видео и YouTube с дополнительными материалами.
GNU GPL v3 или более поздняя версия. Логотип в `src/absorbobot/assets/absorbent.jpg`
взят из Absorbent и распространяется на тех же условиях.

## Раздельная установка

Python не ниже 3.13 и `uv`. Окружение бота не содержит torch или Absorbent:
ядро устанавливается отдельно как non-editable `uv tool` из фиксированного
релиза. Рабочая копия разработки ядра не используется. Для этого развёртывания
выбран проверенный wheel Absorbent **0.1.2**, собранный из точного коммита
тега `v0.1.2`; бот устанавливается из полного опубликованного SHA
репозитория `ivan-mikhnovich/absorbobot`.
`absorbobot check` вызывает `check_runtime()` (внутри него — `probe_core()`),
затем `check_unit_paths()` и `check_telegram()`. Нужен установленный через
`uv tool install`, не editable пакет, полный commit и `dirty=false`.
Версия ядра не закреплена в коде бота.
Файл `uv-receipt.toml`, который `uv` сохраняет в каталоге инструмента
внутри `uv tool dir`, подтверждает установку. Одноразовый запуск через
`uvx` (сокращение для `uv tool run`) без такой установки отклоняется.

```bash
export UV_TOOL_BIN_DIR="$HOME/.local/share/absorbobot/bin"
uv tool install --force 'https://github.com/ivan-mikhnovich/absorbent/releases/download/v0.1.2/absorbent-0.1.2-py3-none-any.whl#sha256=f535b2bb6e6f6bd0d87c27ef874c9db9d8ec1feab8b0faaf2890958eeb814333'
uv tool install --force "git+https://github.com/ivan-mikhnovich/absorbobot.git@${ABSORBOBOT_COMMIT:?Укажите полный опубликованный SHA}"
```

`ABSORBOBOT_COMMIT` — идентификатор проверенного опубликованного коммита,
сохранённый оператором при развёртывании, не имя ветки. Установленный бот
сам не обновляет ни себя, ни ядро.

Единственный каталог моделей — серверная конфигурация Absorbent.
`probe_core()` запускает `workers/probe.py` и возвращает `version_info`,
`installed_editable`, `models`, `defaults`, `media_extensions`,
`material_extensions` и `runtime`. Значения API-ключей не читаются.
Дополнительная модель без ключа
остаётся в каталоге, но её выбор нельзя принять в обработку; ключи
проверяются для выбранных провайдеров, не для всех необязательных моделей.

## Конфигурация

Скопируйте [`examples/config.yaml`](examples/config.yaml) в
`~/.config/absorbobot/config.yaml` и настройте пути и `admin_ids`.
`absorbent_config` указывает на отдельный серверный YAML ядра, не на файл
в рабочей копии разработки. Пустой список администраторов отклоняется.

Секреты хранятся только в `~/.config/absorbobot/secrets.env`, принадлежащем
владельцу сервиса, с правами `600`. Имена переменных:

- `ABSORBOBOT_TOKEN` — токен этого бота.
- `TELEGRAM_API_ID`, `TELEGRAM_API_HASH` — application credentials для
  официального локального Telegram Bot API, не токены другого бота.
- API key env names, указанные в серверном YAML Absorbent, например
  `DEEPSEEK_API_KEY`.

При ручном запуске CLI файл разбирается без shell и интерполяции;
уже заданные переменные окружения процесса имеют приоритет. В user systemd
значения сначала загружаются из `EnvironmentFile`, поэтому для смены
секретов изменяют защищённый файл и перезапускают соответствующие службы,
а не рассчитывают на окружение интерактивной оболочки. Native API дополнительно
удаляет bot/cloud ключи через `UnsetEnvironment`. Значения секретов не попадают
в YAML, `jobs.models`, `jobs.snapshot`, argv или опубликованный репозиторий.
Проверки не печатают секреты.

До запуска установите `absorbent` и `absorbobot` как два отдельных `uv tool`,
не в одно Python-окружение. Подготовьте native `telegram-bot-api`,
серверные YAML и секреты. Native сервер нужно
собрать из официального
[`tdlib/telegram-bot-api`](https://github.com/tdlib/telegram-bot-api)
с Git-подмодулями (`git clone --recurse-submodules`) и установить по
`api_binary` из конфигурации.

При первом переключении проверьте `getMe` облачного API: username должен
быть `absorbobot`. Затем через защищённый клиент Bot API выполните
`deleteWebhook` с `drop_pending_updates=false` и `logOut` этого бота.
Не передавайте токен в argv и не печатайте его. Переключение разрешено
только после подготовки собственных `TELEGRAM_API_ID` и `TELEGRAM_API_HASH`:
без них локальный сервер работать не будет. Для уже переключённого бота
повторный облачный `logOut` не нужен.

Помимо Python-зависимостей обязательны `bwrap`, `ffmpeg`, `ffprobe`,
`pdfinfo`, `pdftoppm`, `soffice`, `pandoc`, `lualatex`, `kpsewhich` и `bun`.
LuaLaTeX должен иметь собранный format и установленные TeX-корни: их
обнаружение проверяет `probe_core()`. `uv` должен быть доступен в `PATH`,
а native `telegram-bot-api` — по `api_binary`. pip-зависимости бота
эти системные программы не устанавливают.

После подготовки выполните:

```bash
uv tool run --offline --no-config absorbobot check-storage --config ~/.config/absorbobot/config.yaml
uv tool run --offline --no-config absorbobot install-units --config ~/.config/absorbobot/config.yaml
systemctl --user start absorbobot-api.service
uv tool run --offline --no-config absorbobot check --config ~/.config/absorbobot/config.yaml
systemctl --user start absorbobot.service
```

`check` требует уже работающего локального API. Его успех подтверждает
preflight и идентичность бота, но не заменяет проверку реального диалога,
обработки лекции и доставки файлов.

`check-storage` проверяет только backing mount, доступность записи и
свободное место: не читает секреты, не обращается к API и не создаёт
каталоги. `check` — read-only preflight: проверяет зависимости, установленное
ядро и `getMe` локального Bot API с username `absorbobot`; не обрабатывает
лекции и не отправляет сообщения. `install-units` записывает только
`absorbobot.service` и `absorbobot-api.service` в пользовательский systemd
и выполняет `daemon-reload`, но не запускает сервисы и не меняет чужие units.
После проверки mount `install-units` создаёт собственные рабочие каталоги служб;
символические ссылки вместо этих каталогов или собственных units отклоняются.
Пути в units берутся из выбранной конфигурации. Устаревшие собственные units
после изменения путей выявляет `check_unit_paths()` при `absorbobot check`.
Для проверки сгенерированных служб без их запуска используйте
`systemd-analyze --user verify ~/.config/systemd/user/absorbobot{,-api}.service`.

Локальный сервер Bot API обязателен для любой работы бота; большие записи
требуют его потому, что облачный API ограничивает скачивание файлов.
Сервер слушает только loopback на порту 8081. Облачного запасного режима нет.
Перед переключением нужны собственные application credentials
и корректная установка native `telegram-bot-api`.

## Приём, обработка и выдача

Одна лекция состоит из одной записи или YouTube-ссылки и упорядоченных
дополнительных материалов. Принимаются поддерживаемые установленным
Absorbent аудио, видео, PDF, офисные документы и фотографии.
Исходное имя хранится в `work_files.original_name`; путь хранения создаёт бот.
Пределы по умолчанию из [`examples/config.yaml`](examples/config.yaml):

| Параметр YAML            | Значение          | Ограничение                                                    |
|--------------------------|-------------------|----------------------------------------------------------------|
| `max_media_bytes`        | 2000000000 байт   | Одна запись                                                    |
| `max_media_seconds`      | 14400 секунд      | Длительность записи                                            |
| `max_material_bytes`     | 100000000 байт    | Все материалы вместе                                           |
| `max_material_pages`     | 100 страниц       | Все материалы вместе                                           |
| `max_work_bytes`         | 100000000000 байт | UUID-каталог работы                                            |
| `max_processing_seconds` | 21600 секунд      | Общий дедлайн обработки задания; таймаут одной операции приёма |
| `min_free_bytes`         | 50000000000 байт  | Минимум свободного места                                       |
| `telegram_part_bytes`    | 1900000000 байт   | Одна часть, не больше 2000000000 байт                          |
| `quota_jobs`             | 10 запусков       | Квота обычного пользователя                                    |
| `quota_window_seconds`   | 86400 секунд      | Скользящее окно квоты                                          |

Превышение приводит к отказу или остановке работы, не обрезанию.

YouTube-ссылка должна указывать на одно доступное без входа видео на `youtube.com`,
`www.youtube.com`, `m.youtube.com` или `youtu.be`. Поддерживаются публичные
видео и доступные по ссылке (`unlisted`), не приватные. После проверки
выбирается «Видео» (до 1080p с аудио) или «Только аудио» (M4A). Плейлисты, эфиры,
неизвестная длительность, пользовательские cookies и произвольные сайты
не поддерживаются. `DownloadBudget` ограничивает bytes из progress-хуков
и объём промежуточных файлов; после сборки `media.mkv` или `media.m4a`
размер результата проверяется повторно. `Engine.run()` не запускает
подготовку одновременно с обработкой другого задания.
Подготовка не расходует квоту запусков обработки.

Анализ, загрузка и обработка выполняются через `bwrap`, только с собственным
UUID-каталогом и необходимыми runtime-путями. SSH, домашний каталог,
SQLite и другие задания недоступны. Синтез получает только ключи выбранных
провайдеров; Telegram-ключей в нём нет. Рендер HTML/PDF выполняется отдельно,
без сети и API-ключей. Отказ изоляции останавливает задание, а не включает
запуск без sandbox. Таймаут, предел размера рабочего каталога и недостаток
места также останавливают работу; данные не удаляются автоматически.

Результаты — `notes.md`, самодостаточный `notes.html`, `notes.pdf`
и `notes.zip`. ZIP содержит `notes.md`, `notes.html`, `notes.pdf`,
`images/` при наличии и `transcript.json`, но не исходную запись,
материалы или журнал API.
Все форматы отправляются отдельными документами с привязкой к лекции.
Файл больше `telegram_part_bytes` передаётся частями с исходным именем:
например, `notes.pdf.part001`, `notes.pdf.part002`, … и
`notes.pdf.manifest.json` с порядком, SHA-256 и инструкциями сборки
для Linux/macOS и Windows PowerShell. Части не являются отдельными
архивами; объединение восстанавливает исходный файл без изменения байтов.

Доставка имеет собственное сохранённое состояние для каждого файла
или части. Сбой Telegram не запускает платную обработку заново.
Кнопка `redeliver` создаёт повторную отправку через `Store.record_delivery()`,
не повтор обработки. Прогресс показывает этапы в одном сообщении задания.
Интервал не меньше пяти секунд (`TelegramOutbox.PROGRESS_INTERVAL`)
применяется только к сообщениям прогресса. В SQLite сохраняется время
последней отправки `outbox.sent_at`, поэтому перезапуск не обходит интервал.

## Хранение и транзакции

`storage_dir` должен находиться на явно указанном `backing_mount`
(по умолчанию `/media/storage`), не на корневом диске. Mount и свободное
место проверяются до создания UUID-каталогов; запасного каталога на SSD
нет. Большие файлы располагаются в `storage_dir/jobs/<UUID>/input`,
`output` и `tmp`. Данные сохраняются до явного удаления администратором.

Для SQLite оператор выбирает SSD: `state_dir/absorbobot.sqlite3` должен
находиться вне backing mount; используются WAL, foreign keys и транзакции
`BEGIN IMMEDIATE`. Проверки отвергают размещение на backing mount и NTFS/fuseblk,
но не определяют физический тип накопителя.
Черновик лекции хранится в `drafts` и сохраняет UUID даже при отказе или
закрытии. Принятое задание в `jobs` получает тот же UUID.
При принятии `jobs.snapshot` получает копию `drafts.snapshot`
с настройками, моделями и версией ядра, неизменяемую после принятия.
Изменение настроек или состава черновика сбрасывает `drafts.snapshot`,
не меняя уже принятые задания.

Квота считает задания с `quota_counted=true` за скользящее окно независимо
от статуса: успешные, ожидающие, неудачные и отменённые запуски занимают слот.
Выбор reuse выставляет `quota_counted=false` и освобождает слот.
Учитывается только `accepted_at > now - quota_window_seconds`:
задание точно на границе окна уже не считается.
Повторное подтверждение сводки не создаёт второе задание:
одноразовый token уже потреблён, а черновик имеет состояние `submitted`.
Администратор освобождён от квоты, но его задания стоят в общей FIFO-очереди
и подчиняются тем же пределам входа.

Полный результат — исходное задание `completed`, разрешённый владелец,
`files_deleted=false` и существующие `notes.md`, `notes.html`, `notes.pdf`,
`notes.zip`. Повторное использование готового результата (`reuse`)
требует совпадения `input_signature`: `Store` сравнивает это значение,
которое вычисляет `input_signature()` из `src/absorbobot/intake.py`.
До постановки в очередь `Store.reuse_draft()` создаёт доставку без записи
в `jobs` и без расхода квоты. При позднем совпадении задание уже существует:
оно ждёт выбора в `awaiting_reuse_choice`; `Store.confirm_late_reuse()`
переводит его в `reused` и освобождает слот, не создавая новое задание.
CPU/API расходы исходного результата не переносятся получателю.
Выбор нового запуска повторно проверяет квоту и возвращает задание
в конец очереди с новым `accepted_at`.

Отмена сначала сохраняет намерение. Запись идентичности процесса
в таблице `process_bindings` очищается через `Store.bind_process()` только
после остановки процесса и получения его статуса завершения (`reap`).
Обычная отмена переводит `queued` и `awaiting_reuse_choice` сразу в
`cancelled`, а активное задание — через `cancel_requested` в `cancelled`
после остановки и reap. При восстановлении после аварии
`Store.recover_interrupted()` переводит оставшиеся задания в `preparing`,
`running`, `cancel_requested` и черновики в `preparing` в
`status=failed`, `failure_reason=interrupted`. Черновики `collecting`/`ready`,
очередь и `awaiting_reuse_choice` сохраняются.
`purge` удаляет собственное UUID-дерево задания в `completed`, `failed`,
`cancelled` или `reused`, либо черновика без задания в `closed`, `failed`,
`ready` или `deleted`; наличие процесса блокирует удаление.
История, usage и квота остаются. Удаление задания в `reused`
не удаляет чужой исходный результат. Native API database/cache не является
UUID-деревом и этим действием не очищается.

Telegram update ID, изменения состояния и outbox фиксируются атомарно.
Исходящие действия выполняются отдельно; сетевой сбой доставки не должен
повторно запускать обработку лекции. Bot API не предоставляет client
idempotency: при неизвестном исходе отправки сообщение может повториться.

## Диалог и доступ

Бот принимает только личные обращения допущенных пользователей.
Администраторы из `admin_ids` допущены всегда; остальным нужен
`/allow <numeric_user_id> [label]`, где `label` — метка пользователя.
Проверяется отправитель сообщения
или callback, не username, chat ID или автор пересланной записи.
Неодобренные пользователи и группы не получают ответа; их файлы не загружаются.

Команды: `/start`, `/new`, `/jobs`, `/settings`, `/language`, `/help`,
`/cancel`, `/stats`, `/version`. Приветствие содержит логотип, возможности,
ограничения, предупреждение о хранении и облачных моделях, лицензию,
репозитории и фактическую версию ядра с полным commit.
Начальный язык хранится в `users.language`: Telegram-код с префиксом `ru`
даёт русский, любой другой код или его отсутствие — английский.
Язык конспекта следует `users.language`, пока `users.output_language_override`
равен `NULL`. Действие `reset` очищает `users.settings` и переопределение языка,
возвращая значения `defaults`, полученные от `probe_core()`.
В черновике сохраняется выбранный `youtube_mode`. Кнопка «Как интерфейс»
(`button.same_language`) очищает только переопределение языка конспекта.

Составление лекции: одна запись либо YouTube, затем упорядоченные материалы,
«Файлы добавлены», настройки и подтверждение сводки. Вторая запись не склеивается
с первой: замена требует подтверждения и нового UUID. Незавершённый импорт
не позволяет подтвердить сводку. В разделе дополнительных параметров доступны
все модели текущего каталога и числовые параметры ядра; нечисловые,
бесконечные и недопустимые значения отклоняются без скрытого ограничения.
Исчезнувшую модель требуется выбрать заново, а не молча заменить.

`/jobs` показывает собственную историю. Обычному пользователю `/stats`
показывает только его время, доступные ресурсы и квоту, без денежных показателей.
Администратору `/stats` без аргумента показывает общую статистику с оценкой
расходов; `/stats <numeric_user_id>` — показатели выбранного пользователя.
Для своей истории администратор указывает собственный числовой ID.
Отмена требует подтверждения; активная работа считается остановленной только после reap.
Одноразовые кнопки привязаны к отправителю и действию через `durable_tokens`
и `Store.issue_token()` / `Store.consume_token()`. Повторный update
или подтверждение не создаёт второй запуск.

Администратору доступны `/admin`, `/queue`, `/allow`, `/ban`, `/users`,
`/job <UUID>`, `/stats [numeric_user_id]`, `/storage`, `/purge <UUID>`,
`/pause`, `/resume`. Ban, точечная отмена и purge требуют подтверждения.
Настроенного администратора нельзя заблокировать. Пауза сохраняется
и не прерывает текущую работу. Административная история запрещённых пользователей
остаётся доступной; оценка расходов отделяет известную сумму от неполных вызовов.

## Ресурсы и оценка расходов

Статистика сохраняет время подготовки, ожидания, обработки, рендера
и доставки; HTTP-попытки, включая повторы SDK; usage и сведения о результате.
Подготовка входов учитывается и у drafts без запуска обработки.
Reuse чужого результата учитывает только собственные подготовку
и доставку получателя, не чужие CPU/API расходы.

`cpu_user_seconds`, `cpu_system_seconds` и `ru_maxrss_kib` получают через
`wait4` фактического payload в `workers/supervise.py`, не внешнего bwrap.
`host_rss_peak_kib` — наблюдаемый пик суммы RSS дерева процессов;
`vram_peak_bytes` — наблюдаемый пик process VRAM через NVML (`nvidia-ml-py`).
В `/stats` пиковая память — максимум, не сумма пиков заданий.
`busy_gpu_seconds` — оценка по доступным process utilization samples NVML,
не точное время GPU kernels.
Неподдерживаемые измерения остаются неизвестными с причиной. Локальный
сервер моделей `llama-swap` работает вне дерева процессов задания;
его CPU/GPU и общая загрузка карты не приписываются пользователю.

Деньги доступны только администратору. Оценка API-расходов использует
снимок `src/absorbobot/assets/pricing-2026-10-10.json`, сверенный с
[официальными тарифами DeepSeek](https://api-docs.deepseek.com/quick_start/pricing/),
и timestamp каждой HTTP-попытки: cache hit/miss, output, UTC peak windows
и подтверждённые китайские праздники. Reasoning tokens не прибавляются
повторно к output. Тариф хранится в `tariff_snapshots`, а оценка каждой
попытки — в `api_calls.cost_snapshot`; новые ставки не переписывают
прошлые суммы. Неизвестные usage, тариф
или календарь отмечаются как неполные. Вызовы локального провайдера моделей,
например `llama-swap`, имеют нулевую плату API, но электричество не рассчитано.
Это оценка, не счёт провайдера.
Имена моделей берутся из серверного каталога и не переименовываются ботом.
