# Соглашения репозитория

Правила для каждого коммита в этом репозитории:

- **Сообщения на русском**, корректным академическим стилем. Первая строка —
  краткая суть в прошедшем совершенном виде («Добавлен…», «Исправлен…»,
  «Обновлена версия до…»), **без** conventional-commit префиксов; ссылки на
  классы и функции в квадратных скобках: `[ClassName::method_name()]`.
- После пустой строки — тело: контекст, причина, решение и то, что проверено.
- Сообщение пишется в файл инструментом записи, коммит — `git commit -F
  <файл>`; никогда не использовать `-m` (bash искажает обратные кавычки).
- **Гранулярность**: один коммит на логически завершённую и относительно
  независимую часть; правки поверх неотправленного коммита — через
  `git commit --amend`, а не отдельным коммитом-исправлением.
- **Атрибуция**: автор и коммиттер — пользователь (git исполняется от его
  имени). Бот никогда не указывается автором или коммиттером, trailer
  `Co-authored-by` в сообщение не добавляется.
- **Комментарии в коде** — на русском, каждый заканчивается точкой (`.`).
  Существующие doc-комментарии не удалять; при изменении кода рядом —
  обновлять и их.

## Установка и развёртывание

Пользователь ведёт проект только через агентов: шаги обновления выполняет
агент и доводит их до работающей службы, а не до коммита. Бот и его ядро
работают **из опубликованных артефактов**, никогда из рабочей копии —
editable установку ядра бот отклоняет (проверка в
[`validate_probe()`](src/absorbobot/config.py)).

Порядок установки (полностью — в разделе «Раздельная установка» файла
`README.md`):

```bash
# Ядро: wheel выпущенного GitHub-релиза, digest закреплён в команде.
uv tool install --force 'https://github.com/ivan-mikhnovich/absorbent/releases/download/vX.Y.Z/absorbent-X.Y.Z-py3-none-any.whl#sha256=<digest>'
# Бот: полный опубликованный SHA из github master, обёртка — в каталог из README.
UV_TOOL_BIN_DIR="$HOME/.local/share/absorbobot/bin" uv tool install --force "git+https://github.com/ivan-mikhnovich/absorbobot.git@<полный SHA>"
# Контракт с ядром и перезапуск: юнит запускается через `uv tool run`.
absorbobot check --config ~/.config/absorbobot/config.yaml
systemctl --user restart absorbobot.service
```

- PyPI ни у ядра, ни у бота нет: канал доставки ядра — GitHub Releases, а образ
  в Docker Hub публикует workflow `Docker` ядра по пушу тега `v*`.
- Живой конфиг ядра, который читает бот, — `~/.config/absorbent/config.yaml`;
  он должен совпадать с `config.yaml` репозитория ядра.
- Состояние установленного — в `$(uv tool dir)/<имя>/uv-receipt.toml`;
  служба — `systemctl --user status absorbobot.service` и
  `journalctl --user -u absorbobot.service`.
- Процедура выпуска ядра, установки и проверки доказательствами без Telegram —
  в skill `absorbent-release-deploy`.
- Запись оператора `~/.local/state/absorbobot/deployment.json` ведётся руками:
  кода, который её читает или пишет, нет. После развёртывания в ней обновляют
  текущие `bot` и `core` (версия, commit, tag, адрес и digest wheel ядра) и
  раздел текущего выпуска с проверками; историю проверок не переписывают.
- Правки только документации (`README.md`, `AGENTS.md`) после установки не
  требуют повторной установки и перезапуска службы: wheel их не содержит,
  поэтому commit в receipt — это коммит установленного кода, а не HEAD.

## Связка с ядром

Ядро живёт в `~/devel/absorbent` и задаёт контракт, который бот принимает в
том же проходе, что и правку ядра:

- новое поле у провайдера или модели в probe (`absorbent.config.Provider` и
  `ModelSpec` уходят в ответ через `asdict`) валит
  [`validate_probe()`](src/absorbobot/config.py): набор ключей провайдера
  проверяется как «обязательные есть, лишних нет», а ошибка останавливает и
  `absorbobot check`, и каждое задание (код 2);
- новый этап журнала ядра появляется в живом отчёте только после строки в
  [`reporting.STAGE_OF`](src/absorbobot/reporting.py) и таблице
  `REPORT_ORDER`; этап приёма файла показывается отдельной строкой вне
  таблицы, а ключ `stage.<имя>` в `locales/{ru,en}.json` нужен тесту
  каталога; незнакомый этап молча пропускается, не роняя задание;
- Снимок моделей задания ([`Engine::_snapshot_config()`](src/absorbobot/engine.py))
  ожидает у модели ключи `name`, `spec`, `provider`, `local`, а провайдера
  копирует целиком — так новые поля ядра доезжают до запуска без отдельного кода.

## Аварийная диагностика

- Внутренние ошибки задания перечислены в `INTERNAL_FAILURES`
  ([`store.py`](src/absorbobot/store.py)); для них движок создаёт запись в
  `incidents` и запускает `absorbobot-diagnose@<id>.service`. Пользовательские
  отказы и отмены диагноста не запускают.
- [`IncidentManager`](src/absorbobot/incident.py) пишет промпт и запускает
  отдельный unit через `systemctl --user`; сам бот не ждёт агента. Повторный
  сбой с той же причиной в течение 30 минут подавляется.
- [`run_incident()`](src/absorbobot/incident.py) работает в отдельном процессе:
  шлёт администраторам запуск и полный отчёт, а пользователю — только
  нейтральное сообщение. Отчёт агента читается из `report.md` и `result.json`
  в `<state_dir>/incidents/<id>/`.
- [`SystemdWatchdog`](src/absorbobot/watchdog.py) шлёт `READY=1` и
  `WATCHDOG=1`; `WatchdogSec=120s` в unit и 15-минутный сторож заданий
  ([`Engine::_watchdog()`](src/absorbobot/engine.py)) покрывают зависания.
- Кнопка «Повторить» использует [`Store::retry_job()`](src/absorbobot/store.py)
  и [`reset_work_tree()`](src/absorbobot/config.py): вход сохраняется,
  результаты прошлого запуска удаляются.
- Команда администратора `/fix <комментарий>` создаёт инцидент вида `manual`
  и кладёт в outbox действие `diagnose`; движок вызывает
  [`IncidentManager::start_manual()`](src/absorbobot/incident.py), поэтому
  запуск unit не выполняется внутри транзакции обработки update.
